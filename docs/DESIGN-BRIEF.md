# Design brief — hrabovskyi.online

For a designer picking this site up cold. Everything below is a real constraint of
the running system, not a preference. Where something is negotiable it says so.

---

## What the site is

The personal site of a backend-first .NET engineer in Kyiv. Portfolio, CV, and a
blog. Its job, in order:

1. Make a hiring manager or a peer trust the engineering within about eight seconds.
2. Get the two — soon more — blog posts read to the end.
3. Stay out of the way.

It is **not** a shop, not a SaaS landing page, and not a portfolio for visual work.
There is nothing to convert. The only calls to action are *read the post*, *read the
CV*, *email me*.

Current look: dark terminal-minimal. Single column, 760px measure, monospace accents,
one green and one blue. It is coherent and it is plain. The brief for a redesign is
**not** "make it colourful" — it is "make it feel considered rather than defaulted".

---

## Hard constraints — these break the build or the deploy

The site is **statically exported** (`output: "export"`) and served as flat files by
Caddy behind Traefik behind Cloudflare. There is no Node runtime in production.

| Constraint | Consequence for design |
|---|---|
| **No JS framework runtime for interactivity.** The repo ships **zero `'use client'`** and that is deliberate. | Anything interactive must work as HTML + CSS, or as one small delegated vanilla listener on `document`. No React state, no client components, no animation libraries. |
| **One global stylesheet**, [app/globals.css](../app/globals.css), 509 lines. No Tailwind, no CSS modules, no styled-components, no inline `style={{}}`. | Deliver CSS as plain class names and custom properties that drop into that file. Do not introduce a styling system. |
| **Self-hosted fonts only**, via `next/font/google` in [app/layout.tsx](../app/layout.tsx). | You may change the typefaces, but they must be loadable through `next/font`. Never add a `<link>` to `fonts.googleapis.com` — it puts a render-blocking cross-origin request on the critical path and loses the `size-adjust` fallback metric that keeps CLS at exactly 0. |
| **`next/image` optimization is off.** | Plain `<img>`, or `next/image` with `unoptimized`. Ship correctly sized assets; nothing resizes them at runtime. |
| **A strict CSP** — `script-src 'self'`. | No CDN scripts, no external stylesheets, no remote fonts, no third-party embeds. Everything self-hosted. |
| **`trailingSlash: true`.** | Every internal link carries the slash: `/blog/`, `/posts/foo/`. A link to `/blog` costs a redirect. |
| **OG images are generated by `next/og`** ([lib/og.tsx](../lib/og.tsx)). | That renderer supports **flexbox only — no CSS grid** — and caps the bundle at 500 KB. Design the social card within that. |

Practical reading: this is a **CSS-and-markup redesign**. Typography, colour, spacing,
hierarchy, and the shape of each page. Not a re-platform.

## Accessibility invariants — regressions, already fixed once

Non-negotiable. Each of these was a real failure that got repaired.

- **`:focus-visible` must stay visible.** Never `outline: none` without a replacement of at least equal clarity.
- **Every page needs `<main id="main">`** — the skip link targets it.
- **Interactive targets stay ≥24×24 px** (WCAG 2.5.8).
- **Use `--border-strong`, not `--border`**, on anything whose border is the only boundary of a control. `--border` is a decorative hairline at ~1.3:1; `--border-strong` is 3.11:1 on `--surface`, which is the WCAG 1.4.11 floor.
- **Anything animated needs a `prefers-reduced-motion` escape.**
- **Both themes ship.** Dark is the default; light is a real theme, not an afterthought, toggled via `data-theme` on the root. Any new colour needs a value in both.

Current Lighthouse on mobile, live: **Perf 99 · A11y 100 · Best Practices 100 · SEO 100.**
That is the bar. A redesign that ships at 92 accessibility is a regression, not a
refresh.

## Current design tokens

From `:root` in [app/globals.css](../app/globals.css). Treat as the starting point, not scripture —
but every replacement must clear the same contrast bars.

```css
--bg:            #0a0c10;   /* page */
--surface:       #11151b;   /* cards */
--surface-2:     #161b22;   /* raised */
--border:        #222a34;   /* decorative hairline only */
--border-strong: #5a6578;   /* required on control boundaries — 3.11:1 on --surface */
--text:          #c9d1d9;
--heading:       #e6edf3;
--muted:         #7d8590;
--accent:        #7ee787;   /* green */
--accent-2:      #79c0ff;   /* blue */
--radius:        10px;
--maxw:          760px;     /* the measure */
```

Two accents doing unclear separate jobs is a real weakness — worth resolving rather
than inheriting. Class naming is plain and semantic: `.wrap`, `.card`, `.section-label`.

## Pages and components

Routes: `/` · `/blog/` · `/posts/[slug]/` · `/tags/[tag]/` · `/about/` · `/resume/` ·
`/uses/` · `/now/` · `/search/`

Components, all ~20–30 lines each: `Nav` `Hero` `About` `Projects` `Experience`
`Homelab` `HomelabDiagram` `Contact` `Footer` `PostList` `Picture` `JsonLd`

**Content is data, not JSX.** Projects, experience, skills, homelab entries and links
all live as typed exports in [lib/site.ts](../lib/site.ts); components map over them. This means the
designer can restructure a section's *layout* freely without touching content, and it
means any design that needs a new content field needs a change to that file's types.

Worth knowing per page:

- **`/` (home)** — hero, about, projects, experience timeline, homelab, contact. Currently one long single-column scroll. The most conservative page and the one with the most room.
- **`/posts/[slug]/`** — the page that matters most, and the one with the most existing machinery: a table of contents, heading anchors, per-block copy buttons, Shiki syntax highlighting with **separate light and dark themes**, related posts, prev/next. Long-form reading is the primary job. Get the measure, the rhythm, and the code-block treatment right and the rest follows.
- **`/resume/`** — must **print to PDF cleanly**. There is deliberately no checked-in `cv.pdf`, so the print stylesheet is the deliverable. Needs a real `@media print` pass.
- **`/homelab` section** — a hand-authored SVG diagram. Restyling it means editing SVG.
- **`/search/`** — Pagefind. Its default UI is used today; the markup is largely Pagefind's, so restyle via its CSS hooks.

## Voice

Terse, technical, unsentimental, first person. Concrete over abstract. It admits
mistakes plainly — the flagship post is about a deploy pipeline that was silently dead
for 51 days. The design should match that register: **confident and unadorned**. No
gradients-as-personality, no hero illustration, no "let's build something amazing".

Reference for tone: the two published posts, `content/posts/silent-deploys.md` and
`content/posts/homelab.md`.

---

## What to actually solve

Ranked. This is the useful part.

1. **The site reads as a template with good taste rather than as someone's.** It is competent and anonymous. It needs one memorable, cheap idea — a typographic decision, a grid, a way of handling code — not a coat of paint.
2. **Two accents, no system.** Green and blue with no rule about which means what. Either give them defined jobs or drop to one.
3. **Post typography is generic.** This is the highest-traffic surface and the least designed. Measure, leading, heading scale, code-block density, TOC treatment.
4. **The homepage is one undifferentiated scroll.** Six sections with near-identical visual weight, so nothing leads.
5. **No photograph anywhere on the site.** There is a `hasPicture()` guard on `/about/` waiting for `assets/images/portrait.jpg`. A design that keeps the site imageless should be a decision, not a default.
6. **`/resume/` has no print design**, despite printing being its stated purpose.
7. **The light theme is functional, not designed.** It reads as an inversion.

## Deliverable that fits this codebase best

In descending order of usefulness:

1. A revised `:root` token set — both themes, with contrast ratios stated.
2. A type scale and vertical rhythm, expressed as CSS custom properties.
3. Page-level layout direction for `/` and `/posts/[slug]/`, as annotated static mockups or plain HTML+CSS.
4. An `@media print` sheet for `/resume/`.
5. Anything else as plain CSS against the existing class names.

Figma is fine for exploration, but **the handoff that lands fastest is CSS**, because
there is exactly one stylesheet and no build-time design system to translate through.

## Repo facts a designer will want

- Next.js 16 App Router, React 19, TypeScript. `@/*` maps to the repo root.
- `npm run dev` → localhost:3000. `npm run build` is the real gate — it type-checks and renders every route.
- No tests, no ESLint config.
- CI on every PR: `validate → typecheck → build → caddy validate → lychee` link check.
- **Push to `main` publishes the live site.** Work on a branch.
- Blog posts are `content/posts/*.md`; the filename is the slug. Tags are a **closed vocabulary** in [lib/tags.ts](../lib/tags.ts) and adding one means editing that file *and* `public/admin/config.yml`.
